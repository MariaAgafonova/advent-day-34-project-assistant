# День 33 — AI-поддержка Daily Tasks

**Работающий сервис:** https://day33-support-web.advent-day-18-scheduled-mcp.workers.dev

Результаты проверок и состав поставки: [VERIFICATION.md](VERIFICATION.md).

## Профиль клиента, панель оператора и журнал LLM

В клиентском чате карточка «Профиль клиента» показывает имя, постоянный ID, язык, платформу, версию и дату создания. Перед первой отправкой через интерфейс клиент указывает имя; его можно изменить позже. Имена не уникальны: клиента определяет серверная сессия и ID, а не совпадение имён. Данные профиля сообщены самим клиентом и не подтверждают личность. Карточка отображается при открытии истории, имя также видно в списке обращений и сообщениях. В старых обращениях отображается текущий профиль; исторические снимки имени не создаются. API сохраняет совместимость с прежними анонимными клиентами.

**Панель оператора:** https://day33-support-web.advent-day-18-scheduled-mcp.workers.dev/operator

Панель требует отдельного пароля и показывает обращения всех клиентов, карточку выбранного клиента, историю и его остальные обращения. Это панель просмотра: она не отправляет ответы от человека и не меняет автоматическую обработку чата. Вход в обычную клиентскую сессию не даёт операторских прав.

Первоначальная настройка доступа (из `support`, после заполнения `.dev.vars`):

```powershell
npm run operator:setup
```

Команда генерирует случайный пароль, если `OPERATOR_PASSWORD` ещё не задан, сохраняет его только в игнорируемом `.dev.vars` и загружает в secret Web Worker. Пароль не печатается и не передаётся аргументом процесса. Чтобы войти, откройте локальный `.dev.vars`, скопируйте **значение** `OPERATOR_PASSWORD` и вставьте на странице `/operator`. Для локального входа без загрузки в Cloudflare: `npm run operator:setup -- --local`. Существующий пароль при повторе команды не меняется. Для ротации задайте новое случайное значение длиной не менее 32 символов и повторите настройку; старые операторские сессии перестанут действовать.

Операторская cookie отдельная, HttpOnly/Secure/SameSite=Strict, срок 8 часов; в D1 хранится хеш токена. Проверяются Origin и rate limit входа. В демонстрации один общий операторский пароль, без отдельных сотрудников, ролей и MFA. Для командного использования нужна отдельная полноценная авторизация.

Блок **«Журнал LLM»** доступен под профилем выбранного обращения и клиенту (только своё), и оператору. Для каждого HTTP-вызова видны этап «Поиск по базе знаний» / «Генерация ответа», модель, время начала, длительность, номер попытки, HTTP-статус, результат проверки ответа, токены входа/выхода и общий расход. Также сохранены ID пользовательского сообщения и генерации. При временном сбое каждый повтор — отдельная строка; повтор уже завершённого сообщения новых строк не создаёт. Неизвестный расход показан как «Не сообщено API», а не как ноль. Стоимость в деньгах не рассчитывается.

Журнал не содержит ключей, cookie, промптов, текстов пользователя, ответа провайдера или reasoning content. Пользовательская переписка по-прежнему хранится в `messages`. Для обращений до включения журнала записей нет: они не восстанавливаются задним числом. Если запись результата журнала не удалась, ответ клиенту сохраняется, а запись остаётся незавершённой; отдельная диагностическая ошибка содержит только ID вызова. Автоматического удаления старых журналов пока нет.

Клиентский веб-чат: автоматические ответы DeepSeek по базе знаний, история и контекст клиента через настоящий MCP, сохранение обращений и эскалация в D1. Ответы не требуют одобрения оператора. Учебное приложение Daily Tasks не реализуется; его правила находятся в `../knowledge/support/`.

По согласованному изменению задания используется **только DeepSeek API**. Для RAG выбран **D1 FTS5**, без embeddings, Vectorize, Workers AI и ключа OpenAI. Это полнотекстовый поиск реальных фрагментов, а не заготовленные ответы. Поиск хуже семантического на незнакомых синонимах и формулировках; совпадение слов не доказывает применимость инструкции.

## Архитектура

```text
Браузер → Web/API Worker → D1 (сессия, тикет, сообщения)
                         → MCP SDK Client / Streamable HTTP
                           → Service Binding → CRM MCP Worker /mcp → D1 (контекст)
                         → DeepSeek (короткие поисковые термины)
                         → D1 FTS5 → фрагменты базы знаний
                         → DeepSeek (JSON-ответ) → валидация → D1 → браузер
```

CRM Worker доступен через внутренний Service Binding, `workers_dev=false`. Он проверяет внутренний секрет, серверный scope клиента/тикета и владение. Инструменты `get_customer_context` и `get_ticket_context` принимают только пустой объект. Их не вызывает модель; API вызывает оба через MCP SDK после проверки сессии. Прямого чтения CRM-контекста API для промпта нет. Инициализация, список инструментов и вызовы проходят через настоящий MCP-протокол. RPC-вызов общей функции вместо MCP не используется.

`src/ui` — React; `src/worker.ts` — маршруты; `src/chat.ts` — обработка; `src/mcp-*` — MCP; `src/rag.ts` — FTS5; `src/llm.ts` — DeepSeek и промпт; `scripts/` — индексация/секреты/live-проверка; `migrations/`, `seed.sql`, `tests/` — данные и проверки.

## Установка и локальный запуск

Нужен Node.js 22.12+ (CI: Node 24), npm и для реальных ответов существующий ключ DeepSeek. Команды выполняются из папки `support`:

```powershell
npm ci
Copy-Item .dev.vars.example .dev.vars
```

Заполните `DEEPSEEK_API_KEY`, оставьте выбранную модель `deepseek-v4-flash`. Сгенерируйте случайный `MCP_INTERNAL_SECRET` длиной не менее 32 байт. Значение должно быть одинаковым у обоих Workers. `.dev.vars` исключён из Git; не храните секреты в `artifacts` или переменных `VITE_*`.

```powershell
npm run db:migrate
npm run db:seed
npm run index -- --local
npm run dev
```

Чат: `http://127.0.0.1:8787`. Команда `dev` собирает интерфейс и запускает оба Workers с общим локальным D1. Раздельные команды: `npm run dev:mcp`, `npm run dev:web`; для hot reload интерфейса — `npm run dev:ui` (проксирует API). Используйте одинаковое имя хоста, например `127.0.0.1`, для UI и API.

D1, FTS5, MCP и assets работают локально. Реальные ответы и расширение поискового запроса требуют интернета и DeepSeek; при отсутствии ключа сообщение сохраняется с явной ошибкой. Автоматические тесты работают без реальных ключей.

На Windows `workerd` требует современный Microsoft Visual C++ Runtime x64. На машине реализации системная версия 14.24 вызывала `0xc0000005`; запуск был проверен с локальными runtime DLL 14.40/14.42 из уже установленных NumPy/Python, без замены системных DLL. Эти библиотеки не включены в Git. При чистой установке обновите runtime с официального сайта Microsoft либо запускайте проверки в Linux/CI. Это ограничение инструментария Windows, не опубликованного сервиса.

## Cloudflare: первоначальное развёртывание

Используются обычные Workers + D1, как в проекте дня 20. Платный тариф автоматически не подключается. Конфигурации содержат ID базы текущего демонстрационного аккаунта; для другого аккаунта создайте свою базу и замените `database_id` в обоих файлах.

```powershell
npx wrangler login
npx wrangler d1 create advent-day-33-support
npx wrangler d1 migrations apply advent-day-33-support --remote -c wrangler.web.jsonc
npx wrangler d1 execute advent-day-33-support --remote -c wrangler.web.jsonc --file seed.sql --yes
npm run index -- --remote
npm run deploy:all
```

`deploy:all` собирает UI, публикует сначала закрытый CRM MCP Worker, затем Web Worker и загружает секреты из `.dev.vars` через stdin в Workers secrets. Временные файлы с секретами не создаются. Локальный `ALLOW_INSECURE_LOCAL` в Cloudflare не загружается. Ключ DeepSeek получает только Web Worker. Для повторного развёртывания используйте `npm run deploy:mcp`, `npm run deploy:web`; для обновления секретов — `npm run secrets:upload`.

Повторно **не создавайте базу** при обычном обновлении. Примените только новые миграции, при изменении документации выполните индексацию и публикуйте код. Индексация записывает новый снимок и переключает его после загрузки всех строк; обновления и удаления документов учитываются, повторный запуск не создаёт дублей. Запускайте один индексатор одновременно. Remote import D1 временно блокирует запросы; выполняйте его вне демонстрации. Источники прошлых ответов сохранены отдельными JSON-снимками в сообщениях.

## API и поведение

| Метод | Маршрут | Назначение |
|---|---|---|
| POST | `/api/session` | Создать/восстановить анонимную cookie; тело `{}` |
| POST | `/api/tickets` | Создать обращение; `{subject}` |
| GET | `/api/tickets` | Последние 100 обращений текущего клиента |
| GET | `/api/tickets/:id/messages` | Последние 50 сообщений; `?before=seq` для предыдущих |
| POST | `/api/tickets/:id/messages` | `{content, client_message_id}` |
| POST | `/api/tickets/:id/escalate` | Запросить специалиста; тело `{}` |
| GET | `/api/health` | Наличие базы/индекса и конфигурации; не выполняет платный вызов модели |

Все POST требуют JSON и совпадения Origin с адресом API. Клиент создаётся сервером; браузер не задаёт `customer_id`. Cookie: HttpOnly, SameSite=Lax, Secure в production, срок 30 дней; в D1 хранится SHA-256 токена. Потеря cookie означает потерю доступа к анонимным обращениям, а не восстановление реального аккаунта Daily Tasks.

Лимит сообщения 4000 символов, HTTP-body 16 KiB; лимиты: 10 новых сессий/IP/минуту, 10 сообщений/клиента/минуту, 10 новых тикетов/клиента/минуту. IP используется только как хеш для ограничения частоты. API не логирует тексты, ключи и cookie; ошибки содержат код и `request_id`.

Уникальный `client_message_id` предотвращает повторную вставку. Ошибка модели/MCP оставляет пользовательское сообщение. Кнопка повтора использует тот же ID; повтор завершённого запроса возвращает сохранённый ответ без вызова модели. Новый текст с прежним ID запрещён. В одном тикете одновременно работает одна генерация: D1 compare-and-swap, 120-секундная аренда и идентификатор попытки защищают от запоздалой записи. Общий дедлайн 90 секунд, MCP 10 секунд, расширение запроса 12 секунд; для временных ошибок DeepSeek максимум один повтор. Внешние вызовы не держат транзакцию D1.

MCP возвращает максимум 12 последних сообщений/12 000 символов. Неизвестные платформа/версия помечены `unknown`; структурированные факты не выдумываются и в v1 возвращаются пустым массивом. Поиск использует короткие термины и недавние сообщения; найдено максимум шесть фрагментов/12 000 символов. BM25-счёт используется для ранжирования, произвольного порога уверенности нет. Числовые одноразовые коды, типичные токены и email маскируются перед моделью; это эвристика, а не гарантия удаления любых персональных данных.

LLM возвращает `answer`, `source_ids`, `needs_human`, `escalation_reason`, `suggested_ticket_status`. Zod и проверка ID отклоняют неизвестные источники, неверные статусы и неполный ответ. Проверка схемы не гарантирует фактическую точность. Статус `needs_human` не отменяется генерацией. Оператор может просмотреть обращение в закрытой панели; автоматического подключения к чату, ручных ответов и внешних уведомлений нет.

Дополнительные маршруты: `GET/POST /api/profile`, `GET /api/tickets/:id/llm-calls?before=seq`; закрытые `GET/POST /api/operator/session`, `POST /api/operator/logout`, `GET /api/operator/tickets?customer_id=…&offset=…`, `GET /api/operator/tickets/:id/messages`, `GET /api/operator/tickets/:id/llm-calls`. У клиентских маршрутов проверяется владение, у операторских — отдельная операторская сессия. Отображение профиля в UI читает D1 напрямую; контекст для ответа ассистента продолжает поступать через MCP. Имя клиента в запросы DeepSeek не добавляется.

Обновление существующей установки до профилей/журналов: сначала применить `0002_profiles_and_llm_logs.sql` через обычную команду migrations apply, затем настроить операторский secret и выполнить `npm run deploy:web`. Миграция только добавляет таблицы `llm_calls` и `operator_sessions`; клиенты и переписки сохраняются. Для отката опубликуйте прежнюю версию Web Worker, оставив новые таблицы: прежний код их не использует. Ничего не удалять. MCP Worker для этого обновления менять не требуется.

## Проверки и демонстрация

```powershell
npm run check
npm test
npm run dry-run
npx playwright install chromium
npm run test:e2e
```

Vitest выполняет реальные D1/FTS5 и MCP SDK client/server в Workers runtime, mock заменяет только DeepSeek. Playwright по умолчанию проверяет UI с mock API, без production-секретов. Для проверки **опубликованного полного сервиса с реальным DeepSeek**:

```powershell
$env:SUPPORT_URL = "https://day33-support-web.advent-day-18-scheduled-mcp.workers.dev"
npm run test:live
npm run test:e2e
```

Эти две команды выполняют реальные оплачиваемые запросы по существующему DeepSeek-аккаунту. Отчёты в `artifacts` содержат только синтетические вопросы, ответы и источники; cookie и ключи туда не записываются. Playwright trace отключён для live-прогона, чтобы не сохранять session cookie в сетевой трассе. CI настроен на TypeScript, mock-тесты, сборки и браузерный тест; прежние workflows ревью дня 32 сохранены.

Ручной сценарий: открыть сайт → спросить «Как перенести задачу на завтра?» → раскрыть источники → обновить страницу → убедиться в сохранении истории → нажать «Нужна помощь специалиста». Для проверки учёта истории: «Не приходит email-код. Спам уже проверил»; помощник должен перейти к следующим проверкам.

## Какие данные уходят DeepSeek

Для поисковых терминов: текущий вопрос, тема и максимум два недавних пользовательских сообщения по 500 символов. Для ответа: вопрос, язык/платформа/версия из MCP, ограниченная история, тема/статус обращения и найденные фрагменты учебной документации. ID клиента, cookie, внутренний секрет и данные других клиентов не передаются. Сообщения хранятся в D1; при сетевой неопределённости ID и текст ожидающей отправки временно сохраняются в sessionStorage вкладки, выбранный ID тикета — в localStorage. Не присылайте секреты: исходный пользовательский текст сохраняется в обращении.
